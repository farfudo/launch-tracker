# Feedback Hub — local draft

## Architecture and activation
- Public `POST /feedback` (FastAPI) receives `type`, `message`, optional independent `name`/`email`, and an empty `website` honeypot. Required `Idempotency-Key`: random UUID v4, reused on network retry with identical content. Server assigns `new`, timestamps and returns only `{id, received}`. Visitors cannot send `status` or read feedback.
- Browser uses same-origin `POST /api/feedback` (Next), strict Origin checking, a 16 KiB streamed-body limit, bounded upstream timeout, no cache and generic errors. FastAPI independently enforces the body limit and validation. In production it uses the existing server-only `API_BASE_URL`; `FEEDBACK_API_BASE_URL` optionally separates a local feedback preview from launch fixtures. No credentials are sent to the browser.
- Apply Alembic `20261029_09` to a reviewed staging database first (`cd services/api; alembic upgrade head`). It adds `feedback` and `feedback_rate_buckets` only. Downgrade destroys those tables and their data; back up and approve before using it. No launch, A07 or LL2 changes.
- Intake fails closed unless all API environment settings exist: `FEEDBACK_ENABLED=true`, a random `FEEDBACK_SECRET` of at least 32 characters, `FEEDBACK_CONTROLLER` and `FEEDBACK_PRIVACY_CONTACT`. Configure the last two also on the web service to display the actual controller and privacy contact. Keep the secret server-side in the normal deployment secret manager; stable across replicas/restarts. Secret rotation invalidates older retry digests, returning a safe conflict rather than duplicate success.
- No production migration, deployment or activation has been performed. Before activation, review the controller's legal basis (including an interests assessment if applicable), contact channel, privacy notice, processor agreements, logs and backups, rights-request procedure and retention job. The existence of optional fields does not itself establish a lawful basis.

## Abuse prevention and data handling
- Shared PostgreSQL atomic counters allow 24 valid requests/minute and 500/day globally, across replicas. No IP, browser fingerprint, session identifier or forwarded-address header is collected. These conservative global limits can be exhausted by an attacker, causing temporary denial of intake; decide whether a trusted ingress-level limit is needed before a higher-traffic rollout. No external CAPTCHA/analytics service is used.
- Idempotent insertion has a database unique key and keyed content digest; concurrent same-key/same-payload retries produce one row, changed payload returns 409. Retry keys are not stored in localStorage or cookies. Closing/reloading the page loses the client's retry key; a manually recreated message is a new submission.
- Honeypot rejects populated input with generic validation errors. Types/lengths/email validated server-side. Whitespace-only optional fields become null. SQLAlchemy parameter binding prevents SQL injection; messages are rendered as plain React text, never injected HTML. Do not add body/email/name to application, proxy or exception logs. Access logs must exclude request bodies and headers; database backups need restricted access and expiry too.
- Evaluate with `python -m app.feedback_retention` (counts only, no changes). After reviewing and approving the impact, run **daily** `python -m app.feedback_retention --apply` with the API database environment. It clears optional contacts and the retry digest after 30 days, deletes entire feedback after 180 days, and removes expired aggregate counters/sessions. It outputs counts only. The opt-in workflow and its activation are documented in `OPERATIONS.md`; no production scheduler has been changed by this draft. A message may itself include personal information: the form advises avoiding sensitive content; the whole message still expires at 180 days.
- Receipts allow a visitor to refer to a submission for access/deletion requests; they do not authenticate ownership. Verify requests proportionately before disclosing personal information; anonymous deletion can be processed conservatively by the controller. Responses should use the supplied optional email only for that feedback conversation.
- Privacy reference reviewed: [European Commission — GDPR principles](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/principles-gdpr_en), including minimisation, transparency and storage limitation. This draft's retention durations are product choices, not periods prescribed by GDPR.

## Private administration (follow-up local draft)

A single-administrator login and revocable PostgreSQL sessions are now implemented on the same branch. Administrative routes remain closed unless explicitly configured. The old always-denied placeholder has been replaced by server-side session authorization; no production configuration or deployment has been performed.

See [FEEDBACK_ADMIN.md](FEEDBACK_ADMIN.md) for the Render/Vercel architecture, all server-only environment settings, interactive password-hash generation, migration `20261029_10`, secure cookies, CSRF, shared login limits, activation and recovery. Public intake is unchanged. Do not enable the panel by exposing a frontend key or simply hiding its URL.

## Validation and preview
API tests cover four optional-contact combinations, persistence, malformed email/length/status, honeypot, body size, shared limits, retry deduplication/conflict, retention and default-denied administration. Browser tests cover server-confirmed success, network retry with the same key, disabled double submit, focus return, mobile sizing and translations. PostgreSQL-specific migration/concurrency checks remain required when a local PostgreSQL instance is available; Docker was unavailable during this draft.
